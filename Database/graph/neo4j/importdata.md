# Importing Data into Neo4j

This is a deeper guide to the data-loading methods introduced in [README.MD § Step 4](README.MD) — which one to use, how it works, and full examples. It uses the same airline domain (Customer / Flight / Booking / Ancillary) as the rest of this repo's Neo4j docs, and the Docker setup from [docker-compose.yml](docker-compose.yml) / [gettingstarted.md](gettingstarted.md).

```text
Small CSV, one-off             ──►  LOAD CSV
Huge CSV, empty new database   ──►  neo4j-admin database import (bulk import)
No-code / business user        ──►  Data Importer (Aura / Desktop UI)
JSON, REST APIs, relational DB ──►  APOC (apoc.load.*)
Continuous streams              ──►  Kafka Connector
Spark / big-data pipelines      ──►  Neo4j Connector for Apache Spark
App writes as it runs           ──►  Driver (your own code, parameterised Cypher)
```

---

## 1. Which Method Should I Use?

| Method | Data size | Target database | Code needed | Speed | Best for |
| --- | --- | --- | --- | --- | --- |
| **`LOAD CSV`** | Up to a few million rows | Running, online database | Cypher only | Moderate (transactional writes) | Everyday imports, incremental loads, upserts |
| **Data Importer** (UI) | Small–medium CSVs | Running database (Aura/Desktop/self-managed 5.x+) | None | Moderate | Business users, quick prototypes, visual schema mapping |
| **`neo4j-admin database import`** (bulk/offline) | Millions to billions of rows | **New, empty** database, **offline** | Shell command + CSV | Very fast (parallel, bypasses transactions) | Initial load of a large dataset before going live |
| **APOC `apoc.load.*`** | Any | Running database | Cypher + APOC | Moderate | JSON, XML, REST APIs, JDBC (relational), Parquet |
| **Kafka Connector** | Streaming | Running database | Kafka config, no app code | Continuous | Real-time sync from event streams |
| **Spark Connector** | Big data | Running database | Spark job (Scala/Python) | High throughput | ETL/ELT from data lakes and warehouses |
| **Driver from application code** | Any | Running database | App code (C#, Python, Java, ...) | Depends on batching | Data generated by your app, custom transformation logic |
| **`neo4j-admin database load` / `dump`** | Any | Whole database | Shell command | Fast | Cloning a database, moving between environments (not row-level import) |

**Rule of thumb:** start with `LOAD CSV` for anything that fits in memory and needs transactional safety (constraints enforced row by row). Move to bulk `neo4j-admin database import` only for the **first load** of a genuinely large dataset into an empty database — it can't run against a live database with existing data.

## 2. Before You Import: Constraints and Indexes

Create these **first**. `MERGE` without a matching constraint does a full label scan per row and gets dramatically slower as the graph grows.

```cypher
CREATE CONSTRAINT customer_id IF NOT EXISTS FOR (c:Customer) REQUIRE c.id IS UNIQUE;
CREATE CONSTRAINT flight_key  IF NOT EXISTS FOR (f:Flight)   REQUIRE (f.flightNo, f.date) IS UNIQUE;
CREATE CONSTRAINT ancillary_code IF NOT EXISTS FOR (a:Ancillary) REQUIRE a.code IS UNIQUE;
CREATE INDEX customer_tier IF NOT EXISTS FOR (c:Customer) ON (c.tier);

SHOW CONSTRAINTS;
SHOW INDEXES;
```

A unique constraint auto-creates a backing index, so a separate index for the same property is redundant.

## 3. `LOAD CSV` (Everyday Imports)

### 3.1 Where files live

| Environment | Import folder | Notes |
| --- | --- | --- |
| Docker (this repo's [docker-compose.yml](docker-compose.yml)) | `./neo4j/import` on the host → `/import` in the container | Copy CSVs here before running `LOAD CSV` |
| Neo4j Desktop | Instance's **Open Folder → Import** | Shown in the Desktop UI per-instance |
| Self-managed package install | `/var/lib/neo4j/import` (Linux) or `<install-dir>/import` | Set by `server.directories.import` in `neo4j.conf` |
| Aura | No local filesystem | Use `LOAD CSV FROM 'https://...'` pointing at a public/pre-signed URL, or the Data Importer |

By default Neo4j only reads from the configured import directory (`server.directories.import`), which blocks arbitrary file access. `LOAD CSV FROM 'https://...'` works from anywhere network-reachable, including Aura.

### 3.2 Basic pattern

```bash
cp customers.csv flights.csv bookings.csv ./neo4j/import/
```

```csv
# customers.csv
id,name,tier
C1,Alice,Gold
C2,Bob,Silver
C3,Carol,Blue
```

```cypher
LOAD CSV WITH HEADERS FROM 'file:///customers.csv' AS row
MERGE (c:Customer {id: row.id})
SET c.name = row.name, c.tier = row.tier;
```

Key clauses:

- **`WITH HEADERS`**: access columns by name (`row.id`) instead of position (`row[0]`).
- **`FIELDTERMINATOR ';'`**: for semicolon- or tab-delimited files.
- **`MERGE`**: upsert — creates if missing, matches if present. Requires the constraint from §2 to stay fast.
- **`CREATE`**: always inserts a new node/relationship — faster, but only safe for a genuinely first-time load with no duplicates.

### 3.3 Batching large files (`IN TRANSACTIONS`)

`LOAD CSV` alone runs as **one transaction**, which can exhaust memory on large files. Batch it:

```cypher
:auto LOAD CSV WITH HEADERS FROM 'file:///bookings.csv' AS row
CALL (row) {
  MERGE (c:Customer {id: row.customerId})
  MERGE (f:Flight {flightNo: row.flightNo, date: date(row.flightDate)})
  MERGE (c)-[:BOOKED {pnr: row.pnr}]->(f)
} IN TRANSACTIONS OF 10000 ROWS;
```

- `:auto` (in Cypher Shell/Browser) or `CALL { ... } IN TRANSACTIONS` from a driver commits every N rows, keeping memory bounded.
- Tune the batch size: larger batches are faster per row but hold more memory and lock more; 1,000–10,000 is a common range.
- A failed row inside a batch rolls back **that batch only**, not the whole file — check `db.logs.query` or the query result summary for error counts.

### 3.4 Loading relationships that need both endpoints to exist

Load nodes first, then relationships, or `MERGE` both ends inline (as in §3.2/3.3). For a pure relationship file where both node types were already loaded:

```csv
# ancillary_purchases.csv
customerId,ancillaryCode,purchaseDate
C1,LNG,2026-09-01
C2,WIFI,2026-09-03
```

```cypher
:auto LOAD CSV WITH HEADERS FROM 'file:///ancillary_purchases.csv' AS row
CALL (row) {
  MATCH (c:Customer {id: row.customerId})
  MATCH (a:Ancillary {code: row.ancillaryCode})
  MERGE (c)-[p:PURCHASED]->(a)
  SET p.date = date(row.purchaseDate)
} IN TRANSACTIONS OF 5000 ROWS;
```

Using `MATCH` (not `MERGE`) for nodes here means rows referencing a non-existent customer or ancillary are silently skipped for that `CALL` block unless you add error handling — check row counts against your source file afterward.

### 3.5 Type conversion

CSV values are always strings. Convert explicitly:

```cypher
LOAD CSV WITH HEADERS FROM 'file:///flights.csv' AS row
MERGE (f:Flight {flightNo: row.flightNo, date: date(row.flightDate)})
SET f.durationMinutes = toInteger(row.durationMinutes),
    f.fare             = toFloat(row.fare),
    f.delayed          = toBoolean(row.delayed),
    f.departureTime    = datetime(row.departureTime),   // ISO 8601: 2026-10-01T14:30:00Z
    f.tags             = split(row.tags, '|');           // "wifi|meal|lounge" → list
```

## 4. Data Importer (No-Code UI)

Available in **AuraDB**, **Neo4j Desktop**, and self-managed 5.x+ (Neo4j Query / Browser-based).

1. Open **Data Importer** (Aura console → your instance → **Import**; Desktop → instance → **Data Importer**).
2. **Upload CSV files** (or connect a URL) — one file per node type or relationship type works best.
3. **Map columns to a model**: drag columns onto node labels/properties, then draw relationships between node types in the visual canvas.
4. Mark **unique/key properties** (the tool creates the matching constraints for you).
5. **Run import** — it generates and runs the equivalent `LOAD CSV` + `MERGE` statements in batches.
6. Save the mapping as a reusable template for repeat imports of the same shape.

Good for: prototyping a data model quickly, handing off to a non-technical teammate, or generating a first-draft Cypher script you then refine by hand.

## 5. Bulk Import: `neo4j-admin database import`

For the **initial load** of a large dataset (tens of millions to billions of records) into a **new, empty** database. It writes store files directly, skipping the transaction log — much faster than `LOAD CSV`, but with constraints:

- The target database must be **new and empty** (or you use `--overwrite-destination`).
- The **server must be stopped**, or you import into a **new named database** that hasn't been created yet (Neo4j 5.x+ supports `neo4j-admin database import full <dbname>` while other databases keep running).
- No constraints are enforced during import — duplicate IDs will silently create duplicate nodes unless your CSVs are already clean. Add constraints **after** the import finishes.

### 5.1 File format

Each CSV needs an `:ID`, `:LABEL`/`:TYPE`, and typed columns:

```csv
# customers_nodes.csv
customerId:ID,name,tier,:LABEL
C1,Alice,Gold,Customer
C2,Bob,Silver,Customer
```

```csv
# flights_nodes.csv
flightId:ID,flightNo,date:date,:LABEL
F1,EK501,2026-10-01,Flight
```

```csv
# booked_rels.csv
:START_ID,:END_ID,pnr,:TYPE
C1,F1,ABC123,BOOKED
```

Type suffixes: `:int`, `:long`, `:float`, `:boolean`, `:date`, `:datetime`, `:string[]` (arrays), etc. Omit a suffix for plain strings.

### 5.2 Running the import (Docker)

```bash
# 1. Stop the running database (or use a new, not-yet-created database name)
docker exec neo4j-ee cypher-shell -u neo4j -p 'ChangeMe123!' \
  "STOP DATABASE neo4j"

# 2. Run the bulk importer against the stopped database
docker exec neo4j-ee neo4j-admin database import full neo4j \
  --nodes=Customer=/import/customers_nodes.csv \
  --nodes=Flight=/import/flights_nodes.csv \
  --relationships=BOOKED=/import/booked_rels.csv \
  --overwrite-destination=true \
  --skip-bad-relationships=true \
  --skip-duplicate-nodes=false

# 3. Start it again
docker exec neo4j-ee cypher-shell -u neo4j -p 'ChangeMe123!' \
  "START DATABASE neo4j"
```

Useful flags:

| Flag | Purpose |
| --- | --- |
| `--overwrite-destination=true` | Allow importing into a database that already has (empty) store files |
| `--skip-bad-relationships=true` | Log and skip relationships whose endpoints don't exist, instead of failing the whole import |
| `--skip-duplicate-nodes=true` | Log and skip duplicate `:ID` values instead of failing |
| `--multiline-fields=true` | CSV values contain embedded newlines (e.g. free-text fields) |
| `--high-parallel-io=on` | On fast SSD/NVMe, lets the importer use more parallel I/O |
| `--threads=N` | Cap CPU usage on a shared host |

### 5.3 After a bulk import

```cypher
// Add constraints/indexes now that data is loaded (they'd only slow down the bulk import itself)
CREATE CONSTRAINT customer_id IF NOT EXISTS FOR (c:Customer) REQUIRE c.customerId IS UNIQUE;
CREATE CONSTRAINT flight_id   IF NOT EXISTS FOR (f:Flight)   REQUIRE f.flightId IS UNIQUE;

// Sanity check counts against your source files
MATCH (c:Customer) RETURN count(c);
MATCH ()-[r:BOOKED]->() RETURN count(r);
```

## 6. APOC: JSON, REST APIs, and Relational Sources

APOC ships as a plugin (already enabled via `NEO4J_PLUGINS: '["apoc"]'` in [docker-compose.yml](docker-compose.yml)).

### 6.1 JSON files or APIs

```cypher
CALL apoc.load.json('file:///bookings.json') YIELD value
UNWIND value.bookings AS b
MERGE (c:Customer {id: b.customerId})
MERGE (f:Flight {flightNo: b.flightNo, date: date(b.flightDate)})
MERGE (c)-[:BOOKED {pnr: b.pnr}]->(f);
```

```cypher
// Load from a REST API (paginate if the API supports it)
CALL apoc.load.json('https://api.example.com/bookings?page=1') YIELD value
UNWIND value.results AS b
MERGE (c:Customer {id: b.customerId})
SET c.name = b.name;
```

For authenticated APIs, pass headers:

```cypher
CALL apoc.load.jsonParams(
  'https://api.example.com/bookings',
  {Authorization: 'Bearer ' + $token}, null
) YIELD value
UNWIND value.results AS b
MERGE (c:Customer {id: b.customerId});
```

### 6.2 Relational databases via JDBC

Requires the relevant JDBC driver JAR mounted into `/plugins` and referenced in config (`apoc.jdbc.<alias>.url` or passed inline).

```cypher
// Example: pull from SQL Server (a JDBC driver must be on the classpath)
CALL apoc.load.jdbc(
  'jdbc:sqlserver://sqlhost:1433;databaseName=Airline;user=app;password=***',
  'SELECT customer_id AS id, full_name AS name, tier FROM dbo.Customers'
) YIELD row
MERGE (c:Customer {id: row.id})
SET c.name = row.name, c.tier = row.tier;
```

This is convenient for one-off migrations but embeds credentials in Cypher — prefer environment-based config (`apoc.conf`) or a driver-side ETL script (§8) for anything recurring.

### 6.3 XML and Parquet

```cypher
CALL apoc.load.xml('file:///legacy-export.xml') YIELD value
// walk `value._children` to extract records

CALL apoc.load.parquet('file:///bookings.parquet') YIELD value
UNWIND value AS row
MERGE (c:Customer {id: row.customerId});
```

## 7. Streaming and Big-Data Pipelines

| Connector | What it does | Typical use |
| --- | --- | --- |
| **Neo4j Connector for Kafka** | Sink connector: consumes topics, writes to Neo4j via configurable Cypher templates. Source connector: streams Neo4j changes out via CDC | Real-time sync — e.g. a `bookings` Kafka topic keeps the graph current as orders happen |
| **Neo4j Connector for Apache Spark** | Read/write Neo4j as a Spark DataFrame | ETL from a data lake/warehouse (Databricks, Synapse, EMR) into Neo4j, or exporting graph results into Spark for further analytics |
| **Neo4j Connector for BI tools** (JDBC/ODBC) | Query Neo4j from Power BI, Tableau, etc. | Reporting — not really an "import" path, listed for completeness |

**Kafka sink example (connector config, not Cypher):**

```json
{
  "name": "neo4j-bookings-sink",
  "config": {
    "connector.class": "streams.kafka.connect.sink.Neo4jSinkConnector",
    "topics": "bookings",
    "neo4j.server.uri": "neo4j://neo4j:7687",
    "neo4j.authentication.basic.username": "neo4j",
    "neo4j.authentication.basic.password": "ChangeMe123!",
    "neo4j.topic.cypher.bookings": "MERGE (c:Customer {id: event.customerId}) MERGE (f:Flight {flightNo: event.flightNo}) MERGE (c)-[:BOOKED {pnr: event.pnr}]->(f)"
  }
}
```

**Spark example (PySpark):**

```python
df = spark.read.parquet("s3://airline-data/bookings/")

df.write.format("org.neo4j.spark.DataSource") \
  .mode("Overwrite") \
  .option("url", "neo4j://neo4j:7687") \
  .option("authentication.basic.username", "neo4j") \
  .option("authentication.basic.password", "ChangeMe123!") \
  .option("labels", ":Booking") \
  .option("node.keys", "pnr") \
  .save()
```

## 8. Loading from Application Code (Driver-Based ETL)

Use this when data needs custom transformation logic, comes from multiple sources, or is generated by your own service (see the driver setup in [README.MD § Step 5](README.MD)).

**C# / .NET — batched upsert:**

```csharp
using Neo4j.Driver;

await using var driver = GraphDatabase.Driver(
    "neo4j://localhost:7687",
    AuthTokens.Basic("neo4j", "ChangeMe123!"));

var bookings = LoadBookingsFromSource();   // your own extraction logic

const int batchSize = 1000;
foreach (var batch in bookings.Chunk(batchSize))
{
    await driver.ExecutableQuery(@"
        UNWIND $rows AS row
        MERGE (c:Customer {id: row.customerId})
        MERGE (f:Flight {flightNo: row.flightNo, date: date(row.flightDate)})
        MERGE (c)-[:BOOKED {pnr: row.pnr}]->(f)")
        .WithParameters(new { rows = batch })
        .ExecuteAsync();
}
```

**Python — batched upsert:**

```python
from neo4j import GraphDatabase

driver = GraphDatabase.driver("neo4j://localhost:7687", auth=("neo4j", "ChangeMe123!"))

def load_batch(tx, rows):
    tx.run("""
        UNWIND $rows AS row
        MERGE (c:Customer {id: row.customerId})
        MERGE (f:Flight {flightNo: row.flightNo, date: date(row.flightDate)})
        MERGE (c)-[:BOOKED {pnr: row.pnr}]->(f)
    """, rows=rows)

batch_size = 1000
with driver.session() as session:
    for batch in chunked(bookings, batch_size):   # your own chunking helper
        session.execute_write(load_batch, rows=batch)
```

**Why `UNWIND $rows` beats one query per row:** a single parameterised query with a list parameter sends one network round-trip per batch instead of one per row — often a 10–50× speedup for large loads. This is the same pattern the bulk `LOAD CSV ... IN TRANSACTIONS` uses internally.

## 9. Whole-Database Copy: `dump` / `load`

Not a row-level import — this copies an **entire database** (all data + schema), useful for cloning between environments.

```bash
# Export (Community: offline; Enterprise: can be online with `backup`/`restore` instead)
docker exec neo4j-ee neo4j-admin database dump neo4j --to-path=/data/dumps

# Copy the .dump file to the target environment, then:
docker exec neo4j-ee neo4j-admin database load neo4j --from-path=/data/dumps --overwrite-destination=true
```

Aura also accepts a `.dump` file upload directly in the console (**Import from dump**) — the fastest way to seed a new Aura instance from a local or self-managed database.

## 10. Performance Tips

- **Constraints before `LOAD CSV`, after bulk import** — see §2 and §5.3.
- **Batch everything** — `IN TRANSACTIONS OF N ROWS` for Cypher, `UNWIND $rows` for driver code. Never loop one write per network round-trip.
- **Load nodes before relationships.** `MERGE`ing a relationship whose endpoints don't exist yet either fails or (with plain `MATCH`) silently skips the row.
- **Periodic commit sizing:** start at 1,000–10,000 rows per transaction; larger batches use more memory but reduce per-batch overhead. Watch for `OutOfMemoryError` in `debug.log` and reduce batch size if it appears.
- **Turn off unused indexes during a large `LOAD CSV` import**, then rebuild — fewer indexes to maintain per write means faster loads (skip this for bulk import, which ignores indexes entirely until the end).
- **Multiple small files load faster than one huge file** with `LOAD CSV`, because you can parallelise across sessions; bulk import already parallelises internally.
- **Use `neo4j-admin database import`** instead of `LOAD CSV` once a single load exceeds roughly 10–50 million rows — the constant-time-per-row cost of transactional writes starts to dominate.
- **Validate as you go:** run `MATCH (n) RETURN count(n)` and spot-check a few nodes/relationships after each load stage, rather than only at the very end.

---

## 11. Summary

- **Everyday, safe, incremental loads:** `LOAD CSV ... IN TRANSACTIONS`, with constraints created first.
- **First load of a large, clean dataset into a new database:** `neo4j-admin database import` (bulk/offline).
- **No-code / visual mapping:** Data Importer.
- **JSON, REST APIs, relational sources:** APOC (`apoc.load.*`).
- **Continuous or big-data pipelines:** Kafka Connector / Spark Connector.
- **Custom logic, data from your own app:** driver code with `UNWIND $rows` batching — the same pattern used by every other method under the hood.
- **Cloning a whole environment:** `neo4j-admin database dump` / `load`, or Aura's dump upload.
